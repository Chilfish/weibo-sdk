## 发布事故：npm publish 打包 `catalog:` 依赖 → 0.1.1 重发

**现象**：0.1.0 发布后，`npm i -g @chilfish/weibo-sdk@0.1.0` 报 `EUNSUPPORTEDPROTOCOL: Unsupported URL Type "catalog:"`。

**根因**：维护者手动执行的是 `npm publish`；npm 不解析 pnpm `catalog:` 协议，把 `"axios": "catalog:"` 等原样写进产物 `package.json`。同一源码用 `pnpm pack` 时依赖会被重写为 `^1.20.0` / `^0.2.2` / `^4.5.4`。

**处置**：

- `npm unpublish @chilfish/weibo-sdk@0.1.0 --force`（72 小时内、零依赖方），用 `pnpm publish` 重发 `0.1.1`。
- 核验：registry `dist-tags.latest = 0.1.1`；tarball `dependencies` 正常；临时目录安装后 `node dist/cli.mjs --version` → `0.1.1`。
- 新增 `scripts/verify-publish-tool.mjs`：`prepublishOnly` 检测 `npm_config_user_agent`，非 `pnpm` 直接失败（`npm run prepublishOnly` 已验证 exit 1，`pnpm run prepublishOnly` 通过）。
- 沉淀 [postmortem 010](../postmortem/010-npm-publish-catalog-protocol.md)，并同步 release checklist（禁止 `npm publish`、发布后解包核验依赖）。

**遗留**：

- registry 里还有 `0.0.0-stage`（02:25:40 发布的无依赖 / 无 bin 占位版本），当前 `latest` 已指向 `0.1.1`；npm 页面仍有 CDN 缓存，显示旧标签。
- 本机 `npm i -g` 因 `C:\ProgramData\npm` 权限失败（与包无关），改用 `npm i --prefix <tmp>` 完成安装核验。

## Cookie 支持文件路径（SDK + CLI）

**需求**：`cookie` 参数除了 header 串，还要能直接传完整文件路径，自动读取并解析 Netscape `cookies.txt` 或 header 串内容。

**改动**：

- 新增 `src/utils/cookieInput.ts`：`resolveCookieInput`（路径探测 + 读取 + 解析）+ `parseNetscapeCookies` / `parseCookieHeaderContent`（纯函数，可单测）。
- 解析规则：Netscape 7 列 TSV（支持 `#HttpOnly_`、跳过注释行与过期条目、同名后写覆盖），只保留 `weibo.com` / `weibo.cn` / `sina.com.cn` 域名；header 文件支持 `Cookie:` 前缀与多行；无有效条目 / 路径不存在 / 无微博 Cookie 抛 `InvalidConfigError`（`CONFIG_INVALID`，`context.path` 指路）。
- 浏览器安全：不静态 import `node:fs`，通过 `process.getBuiltinModule('node:fs')` 按需取用；浏览器环境退化为原样字符串（`dist/browser.mjs` 构建与导出面检查通过）。
- 接入点：`WeiboSDK` 构造时解析一次（避免每个 Service 重复读文件）；`AuthService` 兜底（直接构造也生效）；`FetcherService` 请求拦截器改用 `AuthService` 的解析结果；CLI `getCookie` 统一解析并在失败时打印友好错误 + exit 1。
- 测试：`tests/unit/utils/cookieInput.test.ts`（16 例）+ `AuthService` / `getCookie` 文件路径用例。
- 真实文件复核（本机 Netscape 导出）：解析出 6 条微博 Cookie（含 `SUB` / `SUBP` / `XSRF-TOKEN`），header 长度 517；`sdk.checkSession()` 返回 `true`，`whoami --cookie <path>` 退出码 0。

**门禁**：`pnpm test`（223 passed / 18 skipped）/ lint / build / browser-smoke（Node 侧）全绿。

## DX：`searchProfile` 日期参数接受 `YYYY-MM-DD`

**需求**：试玩时拉取近一周微博，发现 `tweet search-profile --starttime` 只能传 unix 秒（`1791820800`）；文档里还残留 `<yyyyMMdd>` 的旧说法。对人和开发者来说，直接写日期更符合直觉。

**提交计划**（未提交，仅记录意图）：

- `feat(utils): parse YYYY-MM-DD date inputs into unix seconds`
- `feat(tweets): accept date strings in searchByDate`
- `docs: record date-string inputs for searchByDate`

**改动**：

- 新增 `src/utils/timeInput.ts`：`resolveTimeInput(value, { boundary, field })` 纯函数。数字 / 纯数字字符串按 unix 秒原样使用；`YYYY-MM-DD` / `YYYYMMDD` 换算为秒（`start` = 当天 00:00:00，`end` = 当天 23:59:59，运行环境本地时区）；日期按本地日历校验，`2026-02-30` 不会滚到 3 月；空串 / 负数 / 非有限数 / 无法识别格式抛 `InvalidConfigError`（`CONFIG_INVALID`，`context.field` 指路）。
- `TweetService.searchByDate`：请求前调用 `resolveTimeInput`（`starttime` 用 `start`、`endtime` 用 `end`），上游仍只收到 unix 秒；`ArchiveService` 传入的数字不受影响。
- CLI `tweet search-profile`：参数说明改为 `YYYY-MM-DD / YYYYMMDD 或 unix 秒`，解析交给 SDK 统一处理。
- 测试：新增 `tests/unit/utils/timeInput.test.ts`（9 例）；`SearchProfile.test.ts` 改为断言日期字符串被换算为秒，并补紧凑日期 / 数字字符串 / 非法日期不发请求（共 6 例）。
- 文档：`cli.md` / `technical-spec.md` / `roadmap.md` / `endpoint-authoring.md` 同步，修正 `cli.md` 里 `<yyyyMMdd>` 与实现不一致的旧说法；`CHANGELOG.md` 记入 Unreleased。

**验证**：`pnpm run typecheck` 通过；`pnpm vitest run tests/unit/utils/timeInput.test.ts tests/unit/services/SearchProfile.test.ts` 15 passed。

## 真实接口复核（OpenCLI browser bridge）

**方式**：复用已登录 Chrome 的 OpenCLI 扩展，在 `weibo.com` 页面内用 `fetch(..., { credentials: 'include' })` 调用端点，原始响应通过 `no-cors` POST 到本机临时 sink（只在 scratchpad，不入库）；再用对应 `EndpointSpec.schema` 对真实响应跑 `safeParse`。

**现有端点**：`user/info`、`user/detail`、`mymblog`、`statuses/show`、`buildComments`、`friendstimeline`、`repostTimeline`、`longtext`、`searchProfile`、`favorites/all_fav`、`favorites/tags`、`friendships/friends`、`followContent`、`side/bandUnified`、`likelist`、`myCmt` 全部通过 schema 校验，**唯一硬错误**是：

- `mymblog.data.since_id` 真实返回 **number**（本账号 `5353953288260002`）或带后缀 **string**（公开账号 `"5348185968740754kp2"`），schema 仍限定 `string` → `API_BAD_RESPONSE`。已改为 `z.union([z.string(), z.number()])`，新增真实 fixture `mymblog_page1_since_id_numeric.json`（脱敏，20 条）并登记 `FIXTURE_RULES` / 组件测试。

**分页行为复测**（与旧文档不一致的地方）：

- `mymblog`：`page=2` 与 `since_id=<第一页 data.since_id>` 返回同一页；`total` 在部分账号为真实总数（6506 / 13718），但 uid `1111681197` 仍返回 `""` + `total: -1` → 漂移是账号相关（或 A/B），不能按单账号结论锁死。分页策略出现过「回摆」，归一化仍以 `page` 为主。
- `favorites/all_fav`：`page=0` → HTTP 400；`tag_id` / `tag=...` 与不带参返回完全一致 → 标签过滤确实只能客户端做。
- `friendships/friends`：`count=5` 与默认都返回 19 条 → `count` 被忽略。
- `buildComments`：只传 `id` → HTTP 400，必需参数（`is_reload` / `is_show_bulletin` / `is_mix` / `type` / `fetch_level`）确认。
- `myCmt`：`cursor=0/1` 与不带参返回同一页 → `cursor` 被忽略；`max_id=<next_cursor>` / `page` 才是有效翻页。
- `likelist`：`page=0` 等同 `page=1`；`page=999` → `{ ok:1, data:{ list: [] } }`。
- `getLikeList`：`cursor=-1` → 空列表 + `next_cursor: -1`。
- `searchProfile`：`starttime=2020-01-01` 字符串被静默忽略（返回全部 600 条）；数字 unix 秒正常过滤。
- `friendstimeline`：**不带 `list_id` 不再 500**，与硬编码 `list_id` 返回同一批数据（2026-08 的结论已过期）。代码保留默认值仅为兼容，注释已同步。
