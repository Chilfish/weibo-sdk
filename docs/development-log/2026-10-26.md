# 2026-10-26

## 范围归档支持 merge 续跑（#20）

**背景**：宿主（weibo-archiver-app）把 `UserArchiveStore` 当产品库用，范围是「最近 30 天」这类按当天
日期算出的相对区间。昨天跑过一次后今天再跑，`since` 必然差一天，`validateUserArchiveResume` 直接抛
`CONFIG_INVALID`，调用方唯一出口是 `store.clear()`，代价是删掉用户全部归档。

**决策**：新增 `resume: 'strict' | 'merge'`（默认 `strict`，行为不变）：

- `merge` 只校验 uid；用新配置重建 meta（保留 `createdAt` / `user`，`totals` 只留 key 仍命中的），
  按新范围重算切片计划；记录由 `loadRecords()` 保留，已完整的 `mblogId` 仍跳过补全。
- `merge` 沿用 journal 的内容选项 / 切片天数，但 `since` / `until` 不继承，缺省按正常默认值解析，
  这样「最近 N 天」每次都会推进，而不是把旧的 `until` 冻结下来。
- 续跑失败单独拆出 `ResumeMismatchError` / `RESUME_MISMATCH`，`context.field = 'resume'`、
  `context.mismatch` 指向具体字段；类继承 `InvalidConfigError`，下游现有 `instanceof` 判断不受影响。
- CLI 增加 `--resume strict|merge`。

**顺带修复**：`FileUserArchiveStore.loadRecords()` / `loadIssues()` 原先按当前 `meta.slices` 读取，
`merge` 重写 meta 后旧 key 的 journal 就读不到了。改为扫描进度目录下全部 `*.journal.jsonl`。

**涉及**：`types/archive/IUserArchive`、`models/errors/ConfigError`、`userArchive/config`、
`UserArchiveService`、`cli/archiveUser/{store,commands}`、`cli.ts`，以及公开文档、CHANGELOG、测试。

**未做（issue 建议中的后续项）**：

- 切片 key 按绝对边界对齐（B）：当前 key 仍以 `since` 为锚，`since` 变化会丢 checkpoint，
  但记录保留 + `completed` 集合已经保证「只补枚举和缺失补全」，稳定 key 属于进一步省请求的优化。
- 只读的 `getJournal()` / `getResumeState()`（E）：宿主的 store 是自己实现的，可直接 `loadMeta()`。
