## 归档脚本模块化

**触发**：`scripts/archive-user.ts` 已经有 1281 行，参数解析、日期切片、journal、并发补全、最终合并和顶层编排全部堆在一个文件里。每加一个开关或调整续跑语义都要在同一个文件里来回跳，难读也难测。

**判断**：

- **行为不变**：命令行参数、journal 文件格式、续跑规则、归档 JSON 结构全部保持原样，只调整代码组织。唯一顺带修掉的是 `buildConfig` 对 `--comment-order` 默认值的隐式依赖——现在缺省时自己回落到 `time`，单独调用也成立。
- **按职责拆模块**，不做框架级重写：继续用 `node:util` 的 `parseArgs`。续跑校验需要知道「用户显式传了哪些参数」，`parseArgs` 的 `tokens` 正好提供这个信息；换成 citty 反而要额外保留这层信息。
- **编排收进 `ArchiveJob`**：原来 `run()` 里的 `completed` / `retryTargets` / `attempted` / `pending` 窗口都是闭包变量，现在作为一次运行的状态集中在一个类里，`runner.ts` 只负责从命令行走到 job，再走到输出。
- **IO 与纯逻辑分开**：切片计划、配置校验、issue 归一化、去重、统计都是纯函数，单独成模块并补离线测试；文件读写只留在 `journal.ts` / `raw.ts`。

**改动**：

- 新建 `scripts/archive-user/` 目录，拆成 `index` / `runner` / `job` / `archive-one` / `output` / `journal` / `raw` / `config` / `cli` / `slices` / `time` / `concurrency` / `issues` / `types` / `constants`。
- 删除 `scripts/archive-user.ts`；`package.json` 的 `archive:user` 指向 `scripts/archive-user/index.ts`。
- 新增 `scripts/archive-user/README.md`：运行流程、参数、断点续跑、journal 结构、模块职责、修改指引与排障。
- 新增 `tests/unit/scripts/archive-user/` 七组离线测试，共 57 条，覆盖切片边界、CLI 解析与续跑校验、journal 截断修复与去重、raw sidecar、并发窗口、最终合并排序 / 统计 / issue 去重。
- 同步 `docs/README.md` 文档索引、`docs/engineering/archive-schema.md` 的脚本路径、`tests/TEST_INDEX.md` 与 `CHANGELOG.md`。

## 调研：把用户归档脚本产品化

**触发**：脚本重构完成后，`scripts/archive-user/` 仍然只存在于仓库里。npm 包只发布 `dist`，下游拿不到这个能力，遇到「归档某个账号某段时间」只能自己再用 `streamArchive` 拼一遍。

**判断**：

- **SDK 不碰文件系统**：核心入口要能跑在 Node / Worker / 浏览器扩展，journal 和 raw sidecar 留在 CLI；SDK 通过 `UserArchiveStore` 端口或可序列化状态交给调用方。
- **不替代现有 `archive`**：`weibo-cli archive <uid>` 是全量镜像；新增的 `archive user` 是范围归档 + 深度补全，两者语义不同，并存。
- **复用现有原子能力**：切片枚举继续用 `ArchiveService.streamArchive({ timelineSource: 'search', sliceWindow })`，补全继续用 `tweets.enrich` / `streamComments` / `streamReplies` / `streamReposts`，不复制分页逻辑。
- **入口独立**：`sdk.userArchive` 作为新服务属性，不再把已经 1900 行的 `ArchiveService` 继续撑大。

**产出**：`docs/planning/research-user-archive-integration-2026-10-22.md`，包含 SDK 类型与用法、store 端口、CLI 参数映射、脚本模块到新位置的对照、行为对齐清单、测试计划与实施顺序。入口命名定为 `sdk.userArchive.stream/run`，CLI 定为 `weibo-cli archive user <uid>`。

## 调研：微博「那年今日 / 微博回忆」接口

**触发**：需要确认「那年今日」是否有稳定接口，以及入口 `containerid=232544_-_index` 是固定值还是可以动态发现。

**抓包结论**：

- 唯一数据端点是 `GET https://m.weibo.cn/api/container/getIndex?containerid=232544`；`_-_` 后缀可选且被忽略。
- **单页、无分页、无日期参数**：`page` / `since_id` / `count` / `date` / `day` / `starttime` / `uid` 全部被忽略，固定返回服务器当天往前 3 年。
- **必须登录 Cookie**：访客 token 返回 `ok:0 + "这里还没有内容"` 的假空；无 Cookie 返回 HTTP 432。
- `232544` 是产品级常量：不按 uid 拼接（`actionlog.cardid` 才拼 uid），不在 H5 bundle 里，个人页响应里出现的 `232544` 是 Referer `lfid` 回显。App「我」页的「那年今日」卡片是唯一入口，PC 端无等价能力。
- 卡片协议：`11` 容器 / `22` banner / `101` 年份头 / `9` mblog / `6` 分享按钮；mblog 无 `mblogid`，用 `bid` 或 `midToMblogId(mid)` 补齐；同一年内顺序不保证时间倒序。

**判断**：

- 接入时应新增独立 spec（`auth: 'cookie'`），不复用 `auth: 'guest'` 的 `mobileContainerSpec`，避免 guest 拿到假空。
- 归一化复用 `extractMobileMblogs`，额外按 `101` 年份头分组并按 `created_at` 排序。
- 上游改 `232544` 或当天无数据时都表现为 `ok:0` + 空 `cards`，需要靠 E2E / 宽事件观察。

**产出**：`docs/planning/research-weibo-memories-2026-10-22.md`（端点契约、参数矩阵、鉴权边界、containerid 发现结论、SDK/CLI/测试建议、未确认项）。

**决策（同日）**：**暂不实施**。能力面太窄（单页、最多 3 年、不能指定日期、只能看登录账号自己），且与 `tweets.searchByDate` 的按日期回溯能力重叠。文档保留为「暂缓实施计划」：第 6 节包含接口协议、类型契约（`IUserMemories`）、endpoint / 归一化 / service / CLI 伪代码、capabilities 条目、测试清单、提交拆分与重新拾起的触发条件；后续有展示或归档需求时直接按该节实现，不需要重新抓包。

## 计划：CLI 终端呈现（`archive user` 试点）

**触发**：`archive user` 的进度 / issue 目前全部按 JSON 行输出到 stderr。对人类来说终端里是一屏 JSON，难以判断整体进度；对管道和 Agent 来说 JSON 又是正确的。两种诉求不应共用一种呈现。

**判断**：

- **日志与进度分开**：日志是 append-only 事件，进度是 last-state 快照。状态行原地刷新，切片完成 / issue 仍然追加，保留 scrollback。
- **单行状态**：多行状态块在终端底部会反复滚动，实测出现抖动和空行；改成单行 `\r` + 清行，只表达当前切片、进度条和计数。
- **stdout / stderr 分工不变**：stdout 仍是一行 `done` JSON；stderr 的 `pretty` / `ndjson` 只影响诊断呈现。
- **自动降级**：TTY 且不在 CI / `TERM=dumb` 时 pretty；管道、CI、非 TTY 继续 NDJSON。`--log-format` 显式覆盖，`--no-progress` 关闭动态刷新，`--quiet` 静默。
- **零依赖，不做全屏 TUI**：ANSI + `\r` / 清行即可；不引入 `ink` / `blessed` / `listr2`，不切 alternate screen。
- **先试点**：只改 `archive user`，其它长任务保持原样；确认稳定后再推广。

**产出**：`docs/engineering/cli.md` 的「终端呈现」章节与 `docs/engineering/user-archive.md` 的参数说明；代码落在 `src/cli/terminal/`，由 `archive user` 调用。测试覆盖模式解析、NDJSON 兼容、pretty 行模式、交互式状态行与颜色降级。

## 调研：微博特殊内容格式适配（视频 / 文章 / 投票 / 直播 / 抽奖）

**触发**：现有 `Tweet` 只覆盖图片、视频、音频和通用 `pageInfo`；如果微博带头条文章、微博投票、直播或抽奖，归档与 Agent 视图会丢信息。同时核对 m 站字段时发现视频被漏掉。

**抓包结论**：

- **m 站视频会丢**：m 的 `page_info.object_type` 是数字 `11`、语义在 `type: "video"`；现有 `extractMediaFromPageInfo()` 只认 `media_type === 'video'` / `object_type === 'video'`。
- **m 站 `page_pic` 是对象**：`{ url, width, height }`，现有 `String(page_pic)` 会得到 `"[object Object]"`；`page_info.type` 在 m 站是字符串，现有 `getNumber()` 会变成 0。
- **文章**：PC 在 `page_info.object_type="article"`（标题 `content1`、作者 `content3`）；m 在 `url_objects[].object.object`（`article_summary` / `author` / `ispay`）。正文是 `ttarticle` 页面的 SSR 内联 `htmlStr`，没有 JSON 正文接口，付费文章可能截断。
- **投票**：`object_type="hudongvote"`。PC 在 `page_info.card_info.vote_object`（选项 / 票数 / 比例 / 截止时间）；m 在 `url_objects[].object.object.vote_object` + `vote_dynamic`（JSON 字符串，当前票数，`vote_object.part_info` 可能是 0）。
- **直播**：`object_type="live"`。PC 在 `page_info.media_info`（`live_id` / `real_status` / `live_start_time` / `real_chatroom_users` / `live_ld` / `replay_ld`）；m 在 `url_objects[].object.object`（`stream` / `urls` / `author` / `status` / `stime`）。
- **抽奖**：不是 `page_info`，而是 `url_struct[]` 的链接卡（`url_type: 39`、`lottery.media.weibo.com`）；详情页是 HTML。

**判断**：

- 新增 additive 的 `ITweet.attachments?: TweetAttachment[]`（`article` / `vote` / `live` / `lottery` 判别联合），保留 `pageInfo` 不动。
- P0 先修 m 站视频与 `page_pic` 失真，再上 attachments；`ITweetContext` 投影 attachments，并把「正文未抓取 / 抽奖详情未抓取 / 直播流临时」写进 `unknowns` / `hints`。
- 文章正文抓取、文章列表（`mymblog?feature=10`）、完整热搜榜（`mineBand` / `entertainment`）作为 P2，不进入默认归一化。
- 明确不做点赞 / 投票 / 转发 / 关注等写操作。

**产出**：`docs/planning/research-tweet-special-formats-2026-10-22.md`（PC/m 协议矩阵、6 个归一化 bug、`attachments` 类型、归一化与 context 伪代码、fixture / 测试 / 提交拆分、风险）。

## 计划：归档总数与吞吐

**触发**：`searchProfile` 返回的 `total` 能表示当前范围的总条数，但之前只用于切片内部的翻页停止；状态行看不到整体进度，最终也无法核对覆盖率。另一方面，默认 `concurrency=6` 且令牌桶约 1 req/s，一页 20 条时体感仍然是串行。

**判断**：

- **总数进 meta，不进归档契约**：每个切片第一次拿到 `total` 时写入 `meta.totals`，通过 `progress.overallTotal` 和 `summary.estimatedTotal` / `coverage` 暴露；`ArchiveFile` 不新增字段，避免为展示信息扩展冻结契约。
- **按页并发**：补全窗口默认提到 20，一页 20 条可以全部进入；分页仍然串行，journal 顺序不变。
- **单条内部并行**：`enrich`、评论、转发互不依赖，同时发出；楼中楼在评论拿到后按 4 路并发展开。
- **吞吐旋钮是令牌桶**：`concurrency` 只决定排队数，CLI 默认 `delay=300`、`burst=8`（约 3 req/s）；命中 432 仍由 SDK 全局暂停重试。

**产出**：`UserArchiveMeta.totals`、`UserArchiveProgress.overallTotal`、`UserArchiveSummary.estimatedTotal/coverage`；CLI 状态行与 `done` 摘要展示总数和覆盖率；`completeUserArchiveTweet` 内部并行；离线测试覆盖总数/覆盖率与内部并发。

## 归档合并：从下游脚本到 SDK / CLI

**触发**：下游为了「增量更新后并回原 JSON」自己写了一个 `merge-weibo-archives.ts`：按 `mblogId` 去重，重复时用 `comments * 100 + media * 10 + text.length` 挑一条，再按时间排序。这是归档场景的常规需求，不该让每个调用方各写一份。

**判断**：

- **不照搬整条取舍**。下游的启发式只能二选一，旧归档有 100 条评论、新一次只拉 20 条时会丢数据。改为字段级并集：微博本体仍取更完整的一份（避免深合并后统计字段互相矛盾），评论 / 楼中楼 / 转发按 id 并集。
- **范围取包络，不新增字段**。`query.range` 合并为最早的 `since` + 最晚的 `until`；中间可能有空洞，这点写进文档，不扩契约。`query.estimatedTotal` 直接不输出：不同区间的总数既不能相加也不能取最大值。
- **issue 要做解决判定**。只做并集的话，旧文件里已经修好的错误会永久留在合并结果里，`complete` 再也回不到 `true`。规则是：某个 `mblogId` 在另一份归档里已完整拿到，且对方覆盖了对应阶段（评论 / 转发开关），旧 issue 视为已解决。
- **纯函数下沉到 SDK**，文件读写留在 CLI。`archive merge` 是本地命令，`archive user --merge` 在抓取前先校验基线，避免跑完一小时才发现 uid 不对。
- **幂等 + 与输入顺序无关**。同一份归档重复合并结果不变，因此 `--merge` 续跑、原地合并（`-o a.json a.json b.json --force`）都安全。

**改动**：

- `src/services/public/userArchive/merge.ts` + `src/types/archive/IArchiveMerge.ts`：`mergeArchiveFiles(files, { now? })`，包根导出。
- `src/cli/commands/archiveMerge.ts`：`readArchiveFile` 与 `runArchiveMerge`；默认输出 `weibo-archive-merged.json`，已存在时要求 `--force`。
- `src/cli/commands/archiveUser.ts` + `src/cli.ts`：`--merge` 基线、合并写回、`done` 摘要增加 `merged` / `deduped`。
- 文档：`user-archive.md` 新增「合并归档」章节与规则表，`cli.md` 补命令、参数与命令映射；README / AGENTS.md / TEST_INDEX / CHANGELOG 同步。
- playground：新增离线场景 `archive-merge` 与 `cli:archive-merge`（单文件即演示幂等）。

**测试**：`unit/services/UserArchiveMerge.test.ts` 覆盖并集、正文取舍、range 包络、issue 解决、幂等与顺序无关、跨账号 / 非 v2 拒绝；`unit/cli/archiveMerge.test.ts` 覆盖写盘、BOM、`--force` 保护与非法输入。
